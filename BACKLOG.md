# Backlog

Живой список только важных задач. Выполненные пункты удаляются отсюда после
фиксации результата в [`CHANGELOG.md`](CHANGELOG.md).

Наличие пункта в backlog не разрешает автоматически менять production. Каждая
server/security-задача выполняется только по отдельному запросу владельца, с
проверкой доступа до и после изменения.

Приоритеты:

- `P0` — защита от потери доступа, данных или остановки сервиса;
- `P1` — заметное улучшение надёжности и пользовательского опыта;
- `P2` — полезное улучшение без срочности.

## P0 — безопасно отключить SSH-вход по паролю

**Зачем:** production сейчас разрешает SSH-вход root по паролю. Пароль уже
использовался в переписке, поэтому безопаснее оставить только ключи.

**Что изменится для владельца:** привычная команда
`ssh root@195.63.161.180` продолжит работать с этого Mac через
`~/.ssh/id_ed25519`. Отключается только ввод пароля через интернет.

**Как сделать без риска потерять доступ:**

1. Не закрывать текущую рабочую root SSH-сессию.
2. Убедиться, что доступна web/VNC/recovery console провайдера VPS.
3. Из второй сессии ещё раз проверить вход с `BatchMode=yes` по ключу.
4. Сохранить backup текущих SSH-настроек.
5. Добавить отдельный config-файл с `PasswordAuthentication no` и
   `PermitRootLogin prohibit-password`.
6. Выполнить `sshd -t`; при любой ошибке ничего не применять.
7. Сделать `systemctl reload ssh`, не `restart`.
8. Открыть третью новую root-сессию и проверить команды/логи.
9. Только после успешной проверки закрыть старые сессии и сменить ранее
   использованный root-пароль на случай доступа через консоль провайдера.

**Откат:** пока старая сессия открыта, удалить новый config-файл, выполнить
`sshd -t` и `systemctl reload ssh`. Если сессия потеряна — использовать recovery
console провайдера.

**Готово, когда:** новый вход по ключу работает, вход по паролю отвергается,
прямой просмотр production-логов из Codex по-прежнему работает.

## P0 — добавить swap и ограничить размер systemd journal

**Зачем:** на сервере 1 GB RAM, swap отсутствует, а journal уже занимал около
1 GB. Одновременный `ffmpeg` и скачивание могут привести к OOM; журнал и cache —
к заполнению 10 GB диска.

**План:**

- создать swapfile размером 1–2 GB с правами `600` и добавить его в `/etc/fstab`;
- задать для journald разумный лимит около 200–300 MB;
- один раз безопасно уменьшить старый journal;
- проверить `free -h`, `swapon --show`, `df -h` и работу `sing-box`/бота.

**Готово, когда:** swap активен после перезагрузки, диск ниже 80%, bot и
`sing-box` active. Это не увеличивает стоимость VPS.

## P0 — резервная копия production-секретов

**Зачем:** GitHub намеренно не хранит `.env`, Instagram cookies/session и
локальные bot-токены. При потере сервера одного Git-репозитория недостаточно.

**План:**

- собрать `.env`, `.env.test`, Instagram cookies/session и короткую recovery
  памятку в один зашифрованный архив;
- хранить его вне репозитория и вне VPS: в менеджере паролей или зашифрованном
  облачном/локальном хранилище;
- не помещать приватный архив в Git даже в зашифрованном виде;
- проверить восстановление списка файлов без раскрытия их содержимого.

**Нужно от владельца:** один раз выбрать место хранения и пароль/ключ шифрования.

**Готово, когда:** новый сервер можно восстановить по GitHub + архиву без поиска
секретов в старых чатах.

## P1 — функциональная проверка после каждого deploy

**Зачем:** `systemctl active` доказывает только наличие процесса, но не доступ к
Telegram API и не правильность production token.

**План:** после рестарта запускать `scripts/telegram_smoke_test.py` от
`tgdownload`; `.deployed-revision` записывать только после успешного smoke test.
При ошибке job должна завершаться красным и сохранять предыдущий маркер версии.

**Готово, когда:** зелёный deploy означает одновременно успешный CI, active
service и доступный Telegram bot.

## P1 — заранее отклонять слишком большие входящие Telegram-файлы

**Зачем:** cloud Bot API не даёт скачать входящий файл больше примерно 20 MB.
Сейчас пользователь может сначала выбрать действие и только потом получить
ошибку `file is too big`.

**План:** сохранять `file_size` в callback payload и ещё при получении файла
показывать короткое объяснение с допустимым размером. Не запускать `ffmpeg` и
OpenAI для заведомо недоступного файла.

**Готово, когда:** ошибка объясняется сразу, без ожидания и лишней нагрузки.

## P1 — лёгкий внешний мониторинг

**Зачем:** сейчас о падении бота владелец обычно узнаёт от пользователя.

**План:** выбрать один простой heartbeat-сервис или отдельный systemd timer,
который проверяет Telegram smoke test и отправляет уведомление только при
проблеме. Не устанавливать Prometheus/Grafana на VPS с 1 GB RAM.

**Готово, когда:** длительная остановка production автоматически создаёт одно
понятное уведомление без спама.

## P2 — контролируемые обновления зависимостей

**Зачем:** YouTube регулярно меняет extraction, а GitHub Actions тоже обновляет
runtime. Ручная проверка версий легко забывается.

**План:** добавить Dependabot для Python и GitHub Actions с редким расписанием.
Не включать auto-merge: каждое обновление `yt-dlp`, Telegram library или Actions
сначала проходит CI и при необходимости ручной media smoke test.

**Готово, когда:** новые версии появляются как отдельные проверяемые PR и не
попадают в production без осознанного merge.

## Не добавляем без новой реальной проблемы

- локальный Telegram Bot API на VPS 1 GB;
- тяжёлый monitoring stack;
- платный Instagram proxy по умолчанию;
- Redis/очередь/база данных для текущего небольшого бота;
- большой архитектурный рефакторинг только ради уменьшения числа строк.
