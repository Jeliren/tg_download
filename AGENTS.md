# Инструкции для Codex и других моделей

Перед любыми действиями с production полностью прочитайте
[`docs/OPERATIONS.md`](docs/OPERATIONS.md). Это источник истины по доступам,
секретам, GitHub Actions, деплою, логам, проверкам и откату.

## Краткая карта

- Репозиторий: `Jeliren/tg_download`.
- Источник истины для кода: `origin/main`.
- Production: `root@195.63.161.180`, порт `22`.
- Код на production: `/opt/tg_download`.
- Сервис: `tg_download_bot.service`.
- Runtime-пользователь и CI deploy-пользователь: `tgdownload`.
- Прямой операторский доступ с этого Mac: `root` по локальному
  `~/.ssh/id_ed25519`. Он проверен и не зависит от deploy-ключа GitHub.
- Автодеплой: `.github/workflows/check.yml` после успешного push в `main`.
- Production-секреты: только `/opt/tg_download/.env`, файлы в
  `/opt/tg_download/data/` и GitHub Actions secrets. В Git их не добавлять.

## Обязательные правила работы

1. Перед правками выполнить `git fetch origin` и `git status -sb`. Не считать
   локальную ветку `main` источником истины: начинать от `origin/main` и не
   затирать чужие незакоммиченные изменения.
2. Не выводить содержимое `.env`, cookies, session-файлов, приватных ключей,
   Telegram/OpenAI токенов или паролей ни в терминал, ни в чат, ни в CI logs.
3. Для чтения production-логов сначала проверять прямой root SSH. Ошибка входа
   как `tgdownload` не означает, что root-доступ отсутствует: это два разных
   ключа и два разных маршрута.
4. Обычный деплой делать через push в `main` и GitHub Actions. Прямое изменение
   кода на сервере допустимо только как аварийная мера; затем ту же правку
   обязательно перенести в Git.
5. `.env` и `data/` сохраняются workflow и не приезжают из Git. Изменение
   локального `.env` само по себе production не меняет.
6. После изменения кода прогнать lint, unit tests и compile-check. После деплоя
   проверить commit marker, active-состояние сервиса, Telegram smoke test и
   свежие логи.
7. Не останавливать и не перенастраивать `sing-box`: VPN работает на том же
   сервере и не относится к этому приложению.

Если задача касается только диагностики, выполняйте read-only проверки сразу:
рабочий SSH-доступ уже настроен. Если запрос пользователя включает изменение
проекта, доводите нормальный путь до Git и production, если он явно не попросил
ограничиться локальной правкой.
